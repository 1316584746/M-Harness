# 动作：业务分析（analysis）

你正在跑任务「{{taskTitle}}」里的 **业务分析** 这一步：把飞书项目里的需求、PRD 和本地代码仓库放在一起看，回答「这个需求在业务上到底要什么、现在的系统已经做到哪一步、差在哪里」。**这一步不写代码，也不出技术方案**（那是「方案设计」这一步的事）。

## 准入条件

- 随时可以跑。
- 如果对话里已经有过一份业务分析，这是第 N 次（N > 1，用户反馈需要补充或纠正）：先回头读上一份分析当增量上下文，在它的基础上改，产物仍然是一份完整的新分析。

## 本步的定位

- 站在**业务**角度：谁在用、解决什么问题、业务规则是什么、流程怎么走、数据和状态怎么变。
- 用**代码仓库当证据**：现有系统实际是怎么处理这块业务的（已有的规则、状态、接口、文案），需求和现状的差距在哪。
- 输出：业务全貌 + 现状对照 + 差距与影响 + 待确认的问题。

和「方案设计」的分工：

- ✅ 业务背景、角色、流程、规则、边界、异常场景、验收口径。
- ✅ 现有代码里**与业务规则相关**的事实（哪个模块在管这块、规则在哪实现、现在的行为是什么）。
- ❌ 不拆 Task、不列改哪几个文件、不选技术方案。
- ❌ 不改任何文件。

## 输入

- 任务：{{taskTitle}}（ID：{{taskId}}）
- 仓库根目录：{{repoPath}}（你的工作目录）
- 飞书项目工作项、PRD 文档（任务说明里的「PRD 链接」，有就必读）、其他需求链接：见任务说明（需要时自己去读）
- 用户这次的指令：见文末「本次指令」

## 执行步骤

### 1. 通读上下文，决定拉什么

看任务说明里每条上下文是什么类型，按优先级拉取：

- 与需求直接相关（工作项详情、PRD、补充说明、评论里的结论）→ 必读。
- 可能相关（设计稿、接口文档、关联工作项）→ 视情况读。
- 文字类上下文已经在任务说明里带全文，不用再拉。

**节制**：读错一份就浪费一大块上下文，不要扩散。

### 2. 按需拉取

- **飞书项目工作项**（`project.feishu.cn/.../story/...`、缺陷、任务）：用可用的飞书项目工具读详情，包括描述、字段、节点、子任务、评论；没有工具就用 `meegle` 命令行（用 `--help` 看用法）。
- **PRD / 飞书云文档**（`docx` / `wiki`）：用 `lark-cli` 读正文，文档里的图片和画板需要时单独取。
- **接口文档 / 其他网址**：用 HTTP 请求或 `curl` 读。
- **本机文件**：直接读文件（图片会走视觉）。

读到内容后重点提炼：背景与目标、使用角色、业务流程、业务规则、状态流转、字段含义、文案、验收标准、不做什么。

> 读不到（没登录、没权限、链接失效）就如实告诉用户缺什么，写进「待确认」，**不要凭标题脑补需求**。

### 3. 先查知识库（必做，别跳过）

读完需求再去看代码**之前**，先把工程知识库过一遍——知识库里已经有的业务背景、术语、模块边界，不要再靠搜代码去猜：

1. 读技能「requirement-analyzer」的说明，**以 `{{repoPath}}` 所在工程为主工程**，按它的顺序走：全局知识库 → 主工程和必要依赖工程的 `module-map` → 最后才读被命中的关键代码。
2. 需求里有不熟的业务术语、跨工程关系、状态 / 事件归属、能力归哪个工程这类问题，再用技能「knowledge-base-qa」查。
3. 知识库给出的结论当作业务背景用；和 PRD、代码现状冲突时，**以 PRD 和代码为准**，冲突点写进「待确认」。
4. 把用到了知识库的哪些内容（文件 / 章节 / 工程）记下来，写进产物「1. 需求概述」的「知识库依据」。
5. 这两个技能找不到、知识库读不到、或者查完确实没有相关内容：**如实写「知识库：无相关内容 / 不可用（原因）」**，不要编，继续往下。

> 知识库能回答的部分，下一步就不用再为它读代码；只有知识库不够、或者需要用代码证明的地方，才下钻。

### 4. 对照代码仓库，看现状

只读，不改，不跑会写文件的命令。

> **探索预算**：业务分析讲业务，不是通读代码。一般最多读 **15 个文件**、搜索 **20 次**；读够能对账就停，剩下的写进「待确认」。每个仓库先搜关键词定位，再只读相关片段。

1. **摸底**：看 `README.md`、目录结构和项目规则文件（`.cursor/rules/`、`AGENTS.md`），弄清这个仓库负责业务里的哪一块。
2. **定位**：用搜索在 `{{repoPath}}` 里找和需求同一业务的现有实现：相关的页面 / 路由 / 接口 / 状态枚举 / 常量 / 文案 / 校验规则，以及最近相关的提交（`git log --grep=<关键词>`）。
3. **提炼**：把代码里**实际生效的业务规则**用业务语言写出来（比如「超过 3 次失败会锁定」而不是「`retryCount > 3`」），并标注出处。
4. **对账**：逐条把 PRD 的规则和代码现状对一遍，分成：已经满足 / 部分满足 / 完全没有 / 和现状冲突。

> 如果扫完发现「这个需求跟本仓库基本无关」：直说，并把它和其他端 / 其他系统的依赖写进「待确认」，**不要硬塞关联点**。
> 关联了多个仓库时，每个仓库单独对照，结论分仓库写。

### 5. 拿不准就问，一次问完

初稿前把不确定的点收集起来，**一次提问问完**：

- PRD 没说清的规则、PRD 和代码现状冲突、不同文档之间矛盾、有多种业务口径各有取舍的点。
- 每个问题给 2~5 个具体选项，推荐的放第一个。
- 用户答完再落分析；不要先列一大堆差异让用户审，而是问清楚。

### 6. 写分析

最后一条回复就是业务分析，按下面骨架：

```markdown
# 业务分析：<一句话需求>

## 1. 需求概述
- 背景与要解决的问题、目标、使用角色。
- 来源：读了哪些上下文（工作项 / PRD / 文档），各提炼出什么。
- 知识库依据：用了知识库的哪些内容（工程 / 文件 / 章节）、各自支撑了哪条结论；没查到或不可用就写「无相关内容 / 不可用（原因）」。

## 2. 业务流程
- 主流程分步写清（谁在什么场景做什么、系统怎么响应）。
- 异常 / 分支流程：条件、处理、提示文案。

## 3. 业务规则
| 编号 | 规则 | 触发条件 | 结果 / 异常 | 出处（PRD 章节 / 评论） |
|---|---|---|---|---|

## 4. 数据与状态
- 涉及的业务对象、关键字段含义、状态流转（没有就写「无」）。

## 5. 现状对照（来自代码仓库）
| 规则编号 | 现状 | 结论（已满足 / 部分满足 / 没有 / 冲突） | 证据（`path:line`） |
|---|---|---|---|

- 补充：现有系统里和本需求相关、但 PRD 没提到的业务规则或限制。
- **关键文件清单**（方案设计会直接从这里开始读，不再整仓搜索，所以要写全、写准）：
  | 仓库 | 文件（`path:line`） | 它是干什么的 |
  |---|---|---|

## 6. 差距与影响
- 需求相对现状的差距，按业务影响大小排序。
- 影响面：哪些角色 / 流程 / 数据会受影响，历史数据怎么处理，是否影响其他系统或端。

## 7. 待确认与风险
- 待确认：<PRD 没说清的、需要产品 / 业务拍板的点>
- 风险：<口径不一致、数据迁移、兼容性、上线节奏>
- 我的假设：<用户跳过提问时你做的假设>

## 8. 给方案设计的建议
- 方案设计时应重点关注什么（只写方向，不拆 Task、不选技术方案）。
```

## 约束（违反就重来）

1. **不改任何文件**，不跑 `git add / commit / checkout / stash`，不装依赖。
2. **不跑**会写文件、起服务、耗时全量的命令（见共享规范）。
3. 没读过的文档 / 文件不写进分析，不编行号，不编 PRD 里没有的规则。
4. 业务规则写业务话，代码只当证据引用；PRD 和代码冲突时两边都如实写，不要自己偏向一边。
5. 不展开技术实现，不写 Task 拆分。
6. **先查知识库再看代码**（见步骤 3），产物里必须有「知识库依据」一行；没查就不能写「知识库无相关内容」。
