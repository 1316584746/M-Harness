# 动作：上线检查（release）

你正在跑任务「{{taskTitle}}」里的 **上线检查** 这一步：把**本次改动涉及的每个服务**在上线前后要**新增 / 修改 / 删除的配置**一次列全，交给负责发布的同学照单操作。重点是这几类：**xxl-job 任务、MQ（topic / 队列 / 消费组）、数据库（表 / 字段 / 索引 / 数据）、Nacos 等配置中心、机器上的配置文件 / 环境变量 / 启动参数**。**这一步只出清单，不改代码、不提交、不推送、不去任何环境上执行。**

> 清单只写**本次改动带来的增量**，不是把仓库里所有配置抄一遍。拿不准某项是不是本次新增的，用 `git diff` / `git log -S<关键字>` 证明，证明不了就放进「待确认」。

## 准入条件

- 随时可以跑；最好是「进行开发」或「代码CR」之后、「提测」之前或之后都行。
- 当前工作目录：{{repoPath}}（任务关联了多个仓库时，**逐仓单独检查**，结论分仓库写，最后合并成一张发布顺序）。
- 有关联仓库；否则告诉用户先关联仓库，结束这一步。
- 找不到任何改动（工作区干净、feature 相对基线也没有提交）：写「无改动，没有需要上线的配置」，结束。
- 不是第一次跑（对话里已有上线检查）：先读上一份当增量上下文，改动变了就更新，产物仍是一份完整的新清单。

## 执行步骤

### 1. 确定「本次改动」是哪些

按优先级取，**取到就停，不要混着用**：

1. 对话里最近一次**改动记录**（进行开发的产物）和**方案**：当作线索，告诉你该重点看哪里。线索不等于事实，**最终以 `git diff` 为准**。
2. 用只读 git 还原真实改动，每个仓单独做：
   - 基线分支：优先读已登记仓库的分支约定（`git_repos` 里的 `branches.base`）；没配就看 `origin/test`、`origin/main`、`origin/master` 哪个存在，仍定不了就问用户。
   - `diff <基线>...HEAD --stat` 看文件范围；再加上工作区未提交的改动（`status`、`diff`）。
   - 当前在基线分支或游离 HEAD 上：不要硬做，问用户用哪个分支做来源。
3. 对话里没有改动记录、git 里也还原不出来：直接告诉用户缺什么，**不要凭需求标题猜配置**。

### 2. 逐类扫描（在改动里找，不要全仓乱搜）

对每个仓，在**改动涉及的文件**里（必要时顺着调用关系读相关的代码）逐类找。下面的关键字只是线索，没有这类东西就如实写「无」。

**① xxl-job（定时任务）**
- 找：`@XxlJob("名字")`、`IJobHandler`、`XxlJobHelper`、任务相关的 `Handler` / `Job` 类；改动里新增、改名、删除、改了参数含义的任务。
- 每个任务要给：执行器（`xxl.job.executor.appname`）、JobHandler 名、建议 cron（有依据才写，没有就写「待定」）、路由策略 / 阻塞策略 / 超时 / 失败重试（有依据才写）、任务参数格式、负责人、首次是否要手动触发或补数。
- 改名 / 删除：旧 JobHandler 的任务要在调度中心**下线或改名**，别让它空跑报错。
- 执行器本身是新的（新服务）：还要注册执行器、配置 `admin.addresses`、`accessToken`、端口。

**② MQ（消息队列）**
- 找：`@RocketMQMessageListener`、`@KafkaListener`、`@RabbitListener`、`RocketMQTemplate`、`KafkaTemplate`、`rabbitTemplate`、`StreamListener`、`Consumer` / `Producer` 配置，以及 topic / tag / queue / exchange / routingKey / consumerGroup 的常量或配置项。
- 每个要给：中间件类型、topic（或 queue / exchange）、tag / routingKey、消费组、生产方 / 消费方分别是哪个服务、消息体是否新增 / 变更字段（新旧消费者是否兼容）、是否需要**提前创建** topic / 队列、分区数 / 队列数 / 权限（ACL）、是否有顺序 / 幂等 / 死信要求。
- **新增消费组 / 消费方式变化**：要写首次消费位点（从头还是从最新）。
- 消息格式不兼容变更：写清**先上哪一方**。

**③ 数据库**
- 找：`*.sql`、`db/migration`、`resources/sql`、Flyway / Liquibase 脚本；实体类（`@TableName` / `@TableField` / `@Entity` / `@Column`）、MyBatis `*.xml` / Mapper 里新增或改动的列、表、索引、枚举值、默认值。
- 每个要给：库 / 表、**新增 / 修改 / 删除**哪些列（类型、长度、是否可空、默认值、注释）、索引变化、存量数据要不要回填或订正、有没有字典 / 配置类初始数据要插入。
- 迁移脚本仓库里已有就**引用文件路径**，没有就根据实体 / Mapper 的改动写一份**参考 DDL**，并标明「参考，未执行，上线前请 DBA 复核」。
- 风险提醒：大表加列 / 加索引（锁表、耗时）、非空列没有默认值、删列 / 改类型（要先上代码还是先改库，旧版本代码还在跑会不会报错）。

**④ 配置中心（Nacos / Apollo 等）**
- 找：`@Value("${...}")`、`@NacosValue`、`@ConfigurationProperties`、`@RefreshScope`、`application*.yml` / `*.properties`、`bootstrap.yml` 里**新增 / 改动 / 删除**的配置项；代码里新增的开关（feature flag）。
- 每个要给：配置项 key、所在 **dataId / group / namespace**（从 `bootstrap` / `application` 里读到真值，读不到写「待确认」）、值的含义、各环境建议值（代码里有默认值就写默认值，生产值不知道就写「待填」，**不要编**）、是否动态生效（`@RefreshScope` / 监听）还是要重启、没配会怎样（有默认值 / 启动失败 / 功能不生效）。
- **敏感信息**（密码、密钥、token、AK/SK）：只写 key 和「需要向负责人索取」，**绝不把真实值写进产物**。

**⑤ 机器 / 容器上的配置**
- 找：`Dockerfile`、`docker-compose*.yml`、k8s `*.yaml`、Helm values、`Jenkinsfile` / CI 配置、启动脚本；代码里 `System.getenv` / `System.getProperty` / `-D` 参数；`logback*.xml` / `log4j2.xml`；`nginx*.conf`；读取本地文件路径的代码（`/data/...`、`/etc/...`、证书、白名单文件）。
- 每个要给：哪台 / 哪类机器（或哪个工作负载）、文件路径或环境变量名、要加 / 改什么、权限与属主、是否要重启、是否影响其他服务共用同一份文件。

**⑥ 其他会卡上线的东西（有才写，没有不用凑）**
- 新增 / 变更的**对外依赖**：调用了新的内部服务接口（Feign / Dubbo / HTTP）、新的第三方域名（要开出口白名单 / 网关路由）、新增的 Redis key / 缓存预热、新的对象存储 bucket。
- **权限 / 菜单 / 字典 / 配置表数据**：后台菜单、权限点、枚举字典、运营配置要在各环境录入。
- **发布顺序**：哪些服务要先上、哪些要后上；是否需要灰度、开关默认关闭再逐步打开。
- **回滚**：回滚代码后，新增的配置 / 字段 / 消息会不会让旧版本出错；哪些可以保留、哪些要一并回退。

### 3. 去重、核对，再确认

1. **每一项都要有出处**：`path:line`（读不到行号就写文件路径），能引用 diff 的就引用。没出处的不写进清单，放「待确认」。
2. 同一个配置在多个环境 / 多个仓里出现，合并成一行，在「涉及仓库 / 环境」列写全。
3. 某一类没发现：**写「无」并说明你查了什么**（如「改动文件里没有 `@XxlJob`，也没有新增任务类」），不要整类省略——用户要看到你检查过。
4. 有会影响清单的拿不准的事（不知道生产环境值、不确定服务名、不确定基线分支）：**一次提问问完**，每个问题给 2~5 个选项，推荐的放第一个；用户跳过就在产物里写你的假设。
