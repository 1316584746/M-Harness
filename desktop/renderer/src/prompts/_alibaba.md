# 附：阿里巴巴 Java 开发手册（完整条目）+ 团队补充规范

> 方案设计、进行开发、代码CR 三步都要对照本规范。条目按手册章节整理，标签含义：**【强制】** 必须遵守，违反按问题报；**【推荐】** 尽量遵守，有理由可以不守但要说明；**【参考】** 酌情。
> **适用范围**：Java / SQL / 接口相关的方案和代码；其他语言按仓库现有风格。仓库里有规则文件（`.cursor/rules/`、`AGENTS.md`）或统一的现有写法时，**以仓库为准**，和本规范冲突时在产物里提一句，不要硬改风格。
> **用法**：写方案 / 写代码时对照；代码CR 时逐章扫 diff，按条目引用（如「并发 · 线程池不得用 Executors」），定级见代码CR 动作自己的说明。

## 一、编程规约

### （一）命名风格

1. 【强制】命名不能以下划线或美元符号开始或结束。
2. 【强制】严禁拼音与英文混合，不允许直接使用中文命名（`alibaba`、`hangzhou` 这类国际通用拼音除外）。
3. 【强制】类名用 `UpperCamelCase`；例外：`DO / BO / DTO / VO / AO / PO / UID` 等缩写整体大写。
4. 【强制】方法名、参数名、成员变量、局部变量统一用 `lowerCamelCase`。
5. 【强制】常量全部大写，单词间用下划线，语义完整，不怕名字长。
6. 【强制】抽象类以 `Abstract` 或 `Base` 开头；异常类以 `Exception` 结尾；测试类以被测类名开头、以 `Test` 结尾。
7. 【强制】数组类型与中括号紧挨：`int[] arrayDemo`。
8. 【强制】POJO 里的布尔属性不加 `is` 前缀，否则部分框架序列化出错。
9. 【强制】包名全小写，点分隔的每段只有一个自然语义的英文单词；包名用单数，类名有复数含义时类名可用复数。
10. 【强制】杜绝完全不规范的缩写，避免望文不知义。
11. 【推荐】命名尽量用完整单词组合，做到代码自解释。
12. 【推荐】用了设计模式的模块、接口、类、方法，命名里体现模式（如 `OrderFactory`、`LoginProxy`）。
13. 【强制】接口里的方法和属性不加任何修饰符（`public` 也不加），并写有效的 Javadoc；尽量不在接口里定义变量，一定要定义的必须与接口方法相关且是应用的基础常量。
14. Service / DAO 命名：【强制】对外暴露的服务一定是接口，内部实现类用 `Impl` 后缀；【推荐】形容能力的接口取形容词（如 `AbstractTranslator implements Translatable`）。
15. 【参考】枚举类名带 `Enum` 后缀，枚举成员全大写、下划线分隔。
16. 【参考】方法命名：获取单个对象 `get`；多个 `list`（复数结尾，如 `listObjects`）；统计值 `count`；插入 `save` / `insert`；删除 `remove` / `delete`；修改 `update`。
17. 【参考】领域模型命名：数据对象 `xxxDO`（xxx 为表名）；传输对象 `xxxDTO`；展示对象 `xxxVO`；`POJO` 是 DO / DTO / BO / VO 的统称，禁止命名成 `xxxPOJO`。

### （二）常量定义

1. 【强制】不允许魔法值（未预先定义的常量）直接出现在代码里。
2. 【强制】`long` / `Long` 赋值时数值后用大写 `L`，不用小写 `l`。
3. 【推荐】不要用一个常量类维护所有常量，按功能归类分开维护（缓存相关、系统配置相关等）。
4. 【推荐】常量复用分五层：跨应用共享、应用内共享、子工程内共享、包内共享、类内共享；跨应用的放二方库，应用内的放 `constant` 目录，子工程内的放 `modules` 的 `constant` 目录，包内的放当前包，类内的用 `private static final`。
5. 【推荐】变量值只在固定范围内变化时用枚举；枚举可附带属性（如 `code`、`desc`）。

### （三）代码格式

1. 【强制】大括号：左大括号前不换行、后换行；右大括号前换行；右大括号后有 `else` 等则不换行；表示终止的右大括号后必须换行。
2. 【强制】左小括号与字符之间、右小括号与字符之间都不出现空格；左大括号前需要空格。
3. 【强制】`if / for / while / switch / do` 等保留字与括号之间必须加空格。
4. 【强制】任何二目、三目运算符左右两边都加一个空格。
5. 【强制】缩进 4 个空格，禁止 tab。
6. 【强制】注释的双斜线与内容之间有且仅有一个空格。
7. 【强制】强制类型转换时，右括号与转换值之间不加空格。
8. 【强制】单行不超过 120 个字符；换行时第二行相对第一行缩进 4 个空格，第三行起不再缩进；运算符与下文一起换行；方法调用的点符号与下文一起换行；多个参数换行在逗号后；括号前不换行。
9. 【强制】方法参数在定义和传入时，多个参数逗号后面加空格。
10. 【强制】文件编码 UTF-8，换行符用 Unix 格式（LF）。
11. 【推荐】单个方法总行数不超过 80 行。
12. 【推荐】不要为了对齐上一行的字符而加多余空格。
13. 【推荐】不同逻辑、语义、业务的代码之间插入一个空行（相同业务逻辑和语义之间不插入）。

### （四）OOP 规约

1. 【强制】避免通过对象引用访问类的静态变量或静态方法，直接用类名访问。
2. 【强制】所有覆写方法必须加 `@Override`。
3. 【强制】相同参数类型、相同业务含义才可以用可变参数，避免用 `Object`；可变参数必须放在参数列表最后（提倡尽量不用可变参数编程）。
4. 【强制】对外暴露的接口签名原则上不允许修改；接口过时必须加 `@Deprecated`，并说明新接口或新服务是什么。
5. 【强制】不能使用过时的类或方法。
6. 【强制】`Object.equals` 容易抛空指针，用常量或确定有值的对象调用 `equals`（推荐 `java.util.Objects#equals`）。
7. 【强制】所有整型包装类对象之间的值比较用 `equals`（`Integer` 在 -128~127 有缓存，超出会不相等）。
8. 【强制】任何货币金额，以最小货币单位、整型类型存储。
9. 【强制】浮点数等值判断：基本类型不能用 `==`，包装类型不能用 `equals`；用 `BigDecimal` 或指定误差范围。
10. 【强制】`BigDecimal` 等值比较用 `compareTo()`，不用 `equals()`（会比较精度）。
11. 【强制】禁止用 `BigDecimal(double)` 构造；用 `BigDecimal(String)` 或 `BigDecimal.valueOf(double)`。
12. 【强制】基本类型与包装类型：所有 POJO 属性必须用包装类型；RPC 方法的返回值和参数必须用包装类型；所有局部变量推荐用基本类型。
13. 【强制】定义 DO / PO / DTO / VO 等 POJO 时不设任何属性默认值。
14. 【强制】序列化类新增属性时不要修改 `serialVersionUID`；完全不兼容升级时才修改。
15. 【强制】构造方法里禁止写业务逻辑，初始化逻辑放 `init` 方法。
16. 【强制】POJO 必须写 `toString`；继承了另一个 POJO 时加 `super.toString()`。
17. 【强制】POJO 里不能同时存在属性 `xxx` 对应的 `isXxx()` 和 `getXxx()`。
18. 【推荐】用索引访问 `String.split` 得到的数组时，要检查最后一个分隔符后有无内容，避免 `IndexOutOfBoundsException`。
19. 【推荐】多个构造方法或多个同名方法按顺序放在一起，便于阅读（优先于下一条）。
20. 【推荐】类内方法顺序：公有 / 保护方法 > 私有方法 > getter / setter。
21. 【推荐】setter 的参数名与成员变量名一致（`this.x = x`）；getter / setter 里尽量不加业务逻辑。
22. 【推荐】循环体内拼字符串用 `StringBuilder.append`。
23. 【推荐】`final` 的使用场景：不允许被继承的类、不允许修改引用的域对象、不允许被覆写的方法、不允许运行中重新赋值的局部变量、避免上下文重复使用同一个变量。
24. 【推荐】慎用 `Object.clone`（默认浅拷贝，深拷贝要重写）。
25. 【推荐】访问控制从严：不允许外部直接 `new` 的构造方法必须 `private`；工具类不允许有 `public` / `default` 构造方法；非 static 成员变量与子类共享的用 `protected`，仅本类使用的用 `private`；仅本类使用的 static 成员变量用 `private`，static 成员变量考虑是否 `final`；仅类内部调用的成员方法用 `private`，只对继承类公开的用 `protected`。

### （五）日期时间

1. 【强制】日期格式化的 pattern 里年份用小写 `y`（`YYYY` 是跨年周所在的年，会在年末出错）。
2. 【强制】分清大写 `M`（月）和小写 `m`（分），大写 `H`（24 小时）和小写 `h`（12 小时）。
3. 【强制】获取当前毫秒数用 `System.currentTimeMillis()`，不用 `new Date().getTime()`；更精确用 `System.nanoTime()`；JDK8 统计耗时推荐 `Instant`。
4. 【强制】任何地方都不使用 `java.sql.Date`、`java.sql.Time`、`java.sql.Timestamp`。
5. 【强制】禁止写死一年为 365 天，避免闰年出错。
6. 【推荐】避免公历闰年 2 月问题（闰年 2 月 29 天，一年 366 天）。
7. 【推荐】用枚举值指代月份；用数字时注意 `Date`、`Calendar` 的月份取值是 0~11。

### （六）集合处理

1. 【强制】`hashCode` 和 `equals`：只要覆写 `equals` 就必须覆写 `hashCode`；`Set` 存储的对象必须覆写这两个方法；自定义对象做 `Map` 的键也必须覆写。
2. 【强制】`ArrayList.subList` 的结果不可强转成 `ArrayList`（返回的是内部类 `SubList`）。
3. 【强制】`Map` 的 `keySet()` / `values()` / `entrySet()` 返回的集合不可添加元素。
4. 【强制】`Collections.emptyList()` / `singletonList()` 等返回的是不可变集合，不可增删。
5. 【强制】`subList` 场景下，对父集合的增删会让子列表的遍历、增加、删除抛 `ConcurrentModificationException`。
6. 【强制】集合转数组用 `toArray(T[] array)`，传入类型完全一致、长度为 0 的空数组。
7. 【强制】`Arrays.asList()` 转出的集合不能用修改集合的方法（`add` / `remove` / `clear` 抛 `UnsupportedOperationException`）。
8. 【强制】泛型通配符：`<? extends T>` 接收的集合不能 `add`，`<? super T>` 不能 `get`（PECS 原则：Producer Extends, Consumer Super）。
9. 【强制】无泛型限制的集合赋值给泛型限制的集合时，使用元素前要 `instanceof` 判断，避免 `ClassCastException`。
10. 【强制】不要在 `foreach` 里对元素做 `remove` / `add`；`remove` 用 `Iterator`，并发时对 `Iterator` 加锁。
11. 【强制】JDK7 及以上，`Comparator` 实现要满足三个条件：x,y 与 y,x 的比较结果相反；x>y 且 y>z 则 x>z；x=y 则 x,z 与 y,z 的比较结果相同。否则 `Arrays.sort`、`Collections.sort` 可能抛 `IllegalArgumentException`。
12. 【推荐】集合泛型定义时，JDK7 及以上用 diamond 语法或全省略。
13. 【推荐】集合初始化时指定初始值大小；`HashMap` 用 `HashMap(int initialCapacity)`，`initialCapacity = 元素个数 / 0.75 + 1`。
14. 【推荐】遍历 `Map` 用 `entrySet`，不用 `keySet`（JDK8 用 `Map.forEach`）。
15. 【推荐】注意各 Map 能不能存 null：`Hashtable` 的 K/V 都不允许；`ConcurrentHashMap` 的 K/V 都不允许；`TreeMap` K 不允许 V 允许；`HashMap` 都允许。
16. 【参考】合理利用集合的有序性（sort）和稳定性（order），避免无序、不稳定带来的负面影响。
17. 【参考】利用 `Set` 元素唯一的特性做去重，避免用 `List.contains` 遍历对比。

### （七）并发处理

1. 【强制】获取单例对象要保证线程安全，其中的方法也要线程安全。
2. 【强制】创建线程或线程池时指定有意义的线程名称，方便回溯。
3. 【强制】线程资源必须通过线程池提供，不允许在应用中自行显式创建线程。
4. 【强制】线程池**不允许用 `Executors` 创建**，用 `ThreadPoolExecutor`，明确运行规则，规避资源耗尽（`FixedThreadPool` / `SingleThreadPool` 队列长度为 `Integer.MAX_VALUE` 会堆积；`CachedThreadPool` / `ScheduledThreadPool` 线程数为 `Integer.MAX_VALUE` 会创建大量线程）。
5. 【强制】`SimpleDateFormat` 线程不安全，不要定义为 static（定义了必须加锁，或用 `DateUtils`）；JDK8 用 `Instant` 代替 `Date`、`LocalDateTime` 代替 `Calendar`、`DateTimeFormatter` 代替 `SimpleDateFormat`。
6. 【强制】自定义的 `ThreadLocal` 必须回收，尤其线程池场景（线程会复用），否则影响后续业务并内存泄漏；用 `try-finally` 回收。
7. 【强制】高并发时同步调用要考虑锁的性能损耗：能用无锁结构就不用锁；能锁区块就不锁整个方法体；能用对象锁就不用类锁。
8. 【强制】对多个资源、数据库表、对象同时加锁时，保持一致的加锁顺序，否则可能死锁。
9. 【强制】阻塞等待获取锁时，加锁必须在 `try` 之外，且加锁与 `try` 之间没有可能抛异常的调用，避免加锁成功后 `finally` 里无法解锁。
10. 【强制】尝试机制获取锁（`tryLock`）时，进入业务代码块之前必须先判断当前线程是否持有锁；锁的释放规则同阻塞等待方式。
11. 【强制】并发修改同一记录要避免更新丢失，需要加锁：应用层加锁、缓存加锁、或数据库乐观锁（用 `version` 作为更新依据）。每次访问冲突概率小于 20% 推荐乐观锁，否则用悲观锁；乐观锁重试次数不得小于 3 次。
12. 【强制】多线程并行处理定时任务时，`Timer` 里只要有一个 `TimerTask` 没捕获异常，其他任务会自动终止；用 `ScheduledExecutorService` 没有这个问题。
13. 【推荐】资金相关的金融敏感信息，使用悲观锁策略。
14. 【推荐】用 `CountDownLatch` 异步转同步时，每个线程退出前必须调用 `countDown`，线程里注意 `catch` 异常，确保 `countDown` 被执行，避免主线程 `await` 一直等到超时。
15. 【推荐】避免 `Random` 实例被多线程使用（共享虽线程安全，但竞争同一 seed 会降低性能）；JDK7 之后用 `ThreadLocalRandom`。
16. 【推荐】双重检查锁（double-checked locking）延迟初始化时，把目标属性声明为 `volatile`（JDK5 及以上）。
17. 【参考】`volatile` 能解决多线程内存不可见问题；一写多读可以，多写不行（如 `count++`），用 `AtomicInteger`；JDK8 推荐 `LongAdder`。
18. 【参考】`HashMap` 在高并发 `resize` 时可能出现死链导致 CPU 飙升，注意规避。
19. 【参考】`ThreadLocal` 无法解决共享对象的更新问题，建议用 `static` 修饰。

### （八）控制语句

1. 【强制】`switch` 里每个 `case` 要么用 `continue / break / return` 终止，要么注释说明继续执行到哪个 `case`；每个 `switch` 都必须有放在最后的 `default`，即使什么代码也没有。
2. 【强制】`switch` 的变量是 `String` 且来自外部参数时，必须先判 null。
3. 【强制】`if / else / for / while / do` 必须使用大括号，即使只有一行。
4. 【强制】三目运算符 `condition ? 表达式1 : 表达式2` 里，注意表达式 1、2 类型对齐时自动拆箱导致的 NPE。
5. 【推荐】高并发场景里，避免用「等于」判断作为中断或退出条件（如用 `count == 0` 判断，可能被超过而永远不成立），用大于或小于区间判断。
6. 【推荐】表达异常分支时少用 `if-else`，可改写成 `if (condition) { ... return obj; }` 之后接着写业务逻辑；必须用 `if() … else if() … else …` 时**不要超过 3 层**，超过用卫语句、策略模式、状态模式等实现。
7. 【推荐】除 `getXxx` / `isXxx` 等常用方法外，不要在条件判断里执行复杂语句，把复杂逻辑判断的结果赋给有意义的布尔变量名。
8. 【推荐】循环体里的语句要考虑性能：定义对象、变量、获取数据库连接、不必要的 `try-catch`（能否移到循环体外）等尽量移出循环；循环里不做数据库查询和远程调用（先批量查再处理）。
9. 【推荐】接口入参保护，常见于批量操作的接口（限制单次数量）。
10. 【参考】需要校验参数的方法：调用频次低的、执行时间开销很大的、需要极高稳定性和可用性的、对外提供的开放接口（RPC / API / HTTP）、敏感权限入口。
11. 【参考】不需要校验参数的方法：极有可能被循环调用的、底层调用频度很高的、被声明成 `private` 只被自己代码调用的（且调用方已保证参数合法）。

### （九）注释规约

1. 【强制】类、类属性、类方法的注释必须用 Javadoc（`/** 内容 */`），不得用 `// xxx`。
2. 【强制】所有抽象方法（含接口里的方法）必须有 Javadoc，除了返回值、参数、异常说明外，还要指出该方法做什么事、实现什么功能（实现类有特别要求的要加说明）。
3. 【强制】所有的类都必须添加创建者和创建日期。
4. 【强制】方法内部单行注释写在被注释语句上方另起一行，用 `//`；多行注释用 `/* */`，注意与代码对齐。
5. 【强制】所有枚举类型字段必须有注释，说明每个数据项的用途。
6. 【推荐】与其半吊子英文，不如用中文把问题说清楚；专有名词与关键字保持英文原文。
7. 【推荐】代码修改的同时注释也要修改，尤其是参数、返回值、异常、核心逻辑。
8. 【参考】注释掉的代码要配合说明，而不是简单地注释掉；无用就删除。
9. 【参考】注释要能准确反映设计思想和代码逻辑，并描述业务含义，让别的程序员迅速了解代码背后的信息。
10. 【参考】好的命名、代码结构是自解释的，注释力求精简准确、表达到位。
11. 【参考】特殊注释标记（`TODO` / `FIXME`）要注明标记人与标记时间，并定期处理。

### （十）前后端规约

1. 【强制】前后端交互的 API 要明确协议、域名、路径、请求方法、请求内容、状态码、响应体。
2. 【强制】前后端列表类接口返回为空时，返回空数组 `[]` 或空对象 `{}`，不返回 null。
3. 【强制】服务端发生错误时，返回给前端的响应信息必须包含 HTTP 状态码、`errorCode`、`errorMessage`、用户提示信息四部分。
4. 【强制】前后端交互的 JSON 里，所有 key 必须是小写字母开头的 `lowerCamelCase`，符合英文表达习惯，表意完整。
5. 【强制】`errorMessage` 是前后端错误追踪机制的体现，可以输出到前端隐藏控件或用户端日志里，帮助快速定位问题。
6. 【强制】需要超大整数的场景，服务端一律用 `String` 返回，禁止用 `Long`（JS 精度丢失）。
7. 【强制】HTTP 请求通过 URL 传参时不能超过 2048 字节。
8. 【强制】HTTP 请求通过 body 传内容时必须控制长度，超过最大长度后端解析会出错（`tomcat` 默认 2MB，`nginx` 默认 1MB）。
9. 【强制】翻页场景：用户输入参数小于 1，前端返回第一页给后端；后端发现输入参数大于总页数，直接返回最后一页。
10. 【强制】服务器内部重定向必须使用 `forward`；外部重定向地址必须使用 URL 统一代理模块生成，否则线上用 HTTPS 时浏览器会提示「不安全」，还会带来 URL 维护不一致。
11. 【推荐】服务器返回信息必须标记是否可以缓存，缓存的话客户端可能重用之前的请求结果。
12. 【推荐】服务端返回的数据用 JSON，不用 XML。
13. 【推荐】前后端时间格式统一为 `yyyy-MM-dd HH:mm:ss`，统一为 GMT。
14. 【参考】接口路径里不要加版本号，版本控制在 HTTP 头信息里体现，有利于向前兼容。

### （十一）其他

1. 【强制】使用正则表达式时利用预编译功能：`Pattern` 定义为 `static final`，不要在方法体内 `compile`。
2. 【强制】`Math.random()` 返回 `double`，取值范围 0≤x<1（能取到 0，注意除零）；要整数随机数不要把 x 放大 10 的若干倍再取整，直接用 `Random` 的 `nextInt` / `nextLong`。
3. 【推荐】任何数据结构的构造或初始化都应指定大小，避免数据结构无限增长吃光内存。
4. 【推荐】对于明确停止使用的代码和配置（方法、变量、类、配置文件、动态配置属性等），坚决从程序中清理出去，避免垃圾。

## 二、异常日志

### （一）错误码

1. 【强制】错误码的制定原则：快速溯源、沟通标准化。
2. 【强制】错误码不体现版本号和错误等级信息。
3. 【强制】全部正常、但不得不填充错误码时返回五个零：`00000`。
4. 【强制】错误码为字符串类型，共 5 位：错误产生来源 + 四位数字编号。`A` 表示错误来源于用户（如参数错误、用户安装版本过低、支付超时等），`B` 表示来源于当前系统（业务逻辑出错、程序健壮性差等），`C` 表示来源于第三方服务（中间件异常、第三方服务超时等）。
5. 【强制】编号不与公司业务架构、组织架构挂钩，一年后仍然有效。
6. 【强制】错误码使用者避免随意定义新的错误码。
7. 【强制】错误码不能直接输出给用户作为提示信息使用。
8. 【推荐】错误码之外的业务独立设计原则：错误码分为一级宏观错误码、二级宏观错误码、三级宏观错误码，后面补充细化。
9. 【参考】错误码的前缀用来区分来源，其他统一遵循公司现有错误码规范。

### （二）异常处理

1. 【强制】Java 类库里定义的、可以通过预检查规避的 `RuntimeException`（如 `NullPointerException`、`IndexOutOfBoundsException`）不应该用 `catch` 处理，先判断再用。
2. 【强制】异常不要用来做流程控制、条件控制。
3. 【强制】`catch` 时分清稳定代码和非稳定代码；对非稳定代码的 `catch` 尽可能区分异常类型，再做对应处理。
4. 【强制】捕获异常是为了处理它，不要捕获了却什么都不处理就抛弃；不想处理就抛给调用者；最外层的业务使用者必须处理异常，转化为用户可以理解的内容。
5. 【强制】`try` 块放在事务代码里、`catch` 异常后需要回滚事务时，一定要手动回滚。
6. 【强制】`finally` 块必须对资源对象、流对象进行关闭，关闭时也要 `try-catch`（JDK7 及以上用 `try-with-resources`）。
7. 【强制】不要在 `finally` 块中使用 `return`（会丢弃 `try` 里的 return 和异常）。
8. 【强制】捕获异常与抛出异常必须完全匹配，或者捕获异常是抛出异常的父类。
9. 【推荐】方法的返回值可以为 null，但必须在注释里充分说明什么情况下返回 null；调用方要判空。
10. 【推荐】防止 NPE，注意产生场景：返回包装类型时自动拆箱；数据库查询结果可能为 null；集合里取出的元素可能为 null；远程调用返回的对象一律判空；`Session` 里取的数据；级联调用 `obj.getA().getB().getC()`（可用 JDK8 `Optional`）。
11. 【推荐】抛异常还是返回错误码：对公司外的 HTTP / API 开放接口必须用错误码；应用内部推荐抛异常；跨应用 RPC 优先用 `Result` 方式，封装 `isSuccess()`、错误码、错误简短信息。
12. 【推荐】区分 unchecked / checked 异常，避免直接抛 `new RuntimeException()`，更不允许抛 `Exception` 或 `Throwable`，用有业务含义的自定义异常。推荐业界已定义过的自定义异常，如 `DAOException` / `ServiceException` 等。
13. 【参考】避免出现重复的代码（DRY 原则）。

### （三）日志规约

1. 【强制】不可直接使用日志系统（Log4j、Logback）的 API，要依赖 SLF4J 的 API（`LoggerFactory.getLogger`），便于统一维护。
2. 【强制】日志文件至少保存 15 天（有「周」频次的异常，保存时间应更长）。
3. 【强制】应用中的扩展日志（打点、临时监控、访问日志等）命名：`appName_logType_logName.log`。
4. 【强制】日志输出时，字符串变量之间的拼接用占位符 `{}`，不用 `+` 拼接。
5. 【强制】`trace / debug / info` 级别的日志输出必须做日志级别的开关判断（`if (logger.isDebugEnabled())`），占位符的参数如有较重计算尤其如此。
6. 【强制】避免重复打印日志，在日志配置文件里设置 `additivity=false`。
7. 【强制】异常信息应包括案发现场信息和异常堆栈信息：`logger.error(各类参数或对象 toString + "_" + e.getMessage(), e);`；如果不处理就往上抛。
8. 【推荐】用 `warn` 级别记录用户输入参数错误的情况；`error` 级别只记录系统逻辑出错、异常等重要错误信息，非必要不要打 `error`。
9. 【推荐】谨慎记录日志：生产环境禁止输出 `debug` 日志；有选择地输出 `info` 日志；用 `warn` 记录刚上线的业务行为信息时注意输出量，避免撑爆磁盘，记得上线后降级。
10. 【推荐】日志里要有足够定位问题的上下文（订单号、用户 ID、关键参数），但见下面「个人信息不入日志」。

## 三、单元测试

1. 【强制】好的单元测试遵守 AIR 原则：Automatic（自动化）、Independent（独立性）、Repeatable（可重复）。
2. 【强制】单元测试全自动、非交互式执行；不允许用 `System.out` 人肉验证，必须用 `assert`。
3. 【强制】保持单元测试独立：用例之间不能互相调用，也不能依赖执行先后次序。
4. 【强制】单元测试可重复执行，不受外界环境影响（网络、服务、中间件等）；需要依赖时用 mock 或在本地搭建。
5. 【强制】保证测试粒度足够小，便于精确定位问题；粒度至多是类级别，一般是方法级别。
6. 【强制】核心业务、核心应用、核心模块的增量代码确保单元测试通过。
7. 【强制】单元测试代码必须写在 `src/test/java`，不允许写在业务代码目录下。
8. 【推荐】单元测试基本目标：语句覆盖率 70%；核心模块的语句覆盖率和分支覆盖率都要 100%。
9. 【推荐】编写单测遵守 BCDE 原则：Border（边界值，如循环边界、特殊取值、特殊时间点、数据顺序等）、Correct（正确的输入得到预期结果）、Design（与设计文档相结合）、Error（强制错误信息输入，得到预期的错误结果）。
10. 【推荐】数据库相关的查询、更新、删除操作，不能假设库里数据一定存在，也不能直接操作数据库插入数据，用程序插入或导入数据的方式准备。
11. 【推荐】和数据库相关的单测可设定自动回滚机制，不给数据库造成脏数据（如 `@Rollback`），或者对单测产生的数据有明确的前后缀标识。
12. 【推荐】对不可测的代码适时重构，使代码变得可测，避免为了达到测试要求而写不规范的测试代码。
13. 【推荐】设计评审阶段，开发人员和测试人员一起确定单测范围，单测最好覆盖所有测试用例。
14. 【推荐】单元测试作为质量保障手段，在项目提测前完成，不建议发布后补。
15. 【参考】为了更方便单测，业务代码应遵守设计规约（单一职责、依赖注入等）。

## 四、安全规约

1. 【强制】隶属于用户个人的页面或功能必须做权限控制校验，防止没做水平权限校验就能访问、修改、删除别人的数据（如查看他人手机号、修改他人订单）。
2. 【强制】用户敏感数据禁止直接展示，必须脱敏（如手机号 `137****0969`）。
3. 【强制】用户输入的 SQL 参数严格使用参数绑定或 `METADATA` 字段值限定，防止 SQL 注入，禁止字符串拼接 SQL 访问数据库。
4. 【强制】用户请求传入的任何参数必须做有效性验证。忽略参数校验可能导致：`page size` 过大导致内存溢出；恶意 `order by` 导致数据库慢查询；任意重定向；SQL 注入；反序列化注入；正则输入源串拒绝服务（ReDoS）。
5. 【强制】禁止向 HTML 页面输出未经安全过滤或未正确转义的用户数据。
6. 【强制】表单、AJAX 提交必须执行 CSRF 安全验证。
7. 【强制】使用短信、邮件、电话、下单、支付等平台资源时，必须实现正确的防重放机制（数量限制、疲劳度控制、验证码校验），避免被滥刷、资损。
8. 【推荐】发帖、评论、发送即时消息等用户生成内容的场景必须实现防刷、文本内容违禁词过滤等风控策略。

## 五、MySQL 数据库

### （一）建表规约

1. 【强制】表达是与否概念的字段，必须用 `is_xxx` 命名，类型是 `unsigned tinyint`（1 表示是，0 表示否）。任何字段如果为非负数，必须是 `unsigned`。
2. 【强制】表名、字段名必须使用小写字母或数字，禁止数字开头，禁止两个下划线中间只出现数字。字段名的修改代价很大（无法预发布），要慎重。
3. 【强制】表名不使用复数名词。
4. 【强制】禁用保留字，如 `desc`、`range`、`match`、`delayed` 等。
5. 【强制】主键索引名为 `pk_字段名`；唯一索引名为 `uk_字段名`；普通索引名为 `idx_字段名`。
6. 【强制】小数类型为 `decimal`，禁止使用 `float` 和 `double`（精度丢失，存储的数据范围超出 `decimal` 范围时拆成整数和小数分开存储）。
7. 【强制】存储的字符串长度几乎相等时，使用 `char` 定长字符串。
8. 【强制】`varchar` 是可变长字符串，不预先分配存储空间，长度不要超过 5000；超过则定义为 `text`，独立出一张表，用主键对应，避免影响其他字段的索引效率。
9. 【强制】表必备三字段：`id`（主键）、`create_time`（创建时间）、`update_time`（更新时间）；有逻辑删除的加 `is_deleted`。时间字段用 `datetime`；`id` 为 `bigint unsigned`，单表时自增、步长为 1。
10. 【推荐】表的命名最好是「业务名称_表的作用」，如 `alipay_task`、`force_project`、`trade_config`。
11. 【推荐】库名与应用名称尽量一致。
12. 【推荐】修改字段含义或对字段表示的状态追加时，及时更新字段注释（每个字段加 `COMMENT`）。
13. 【推荐】字段允许适当冗余，以提高查询性能，但必须考虑数据一致；冗余字段应满足：不是频繁修改的字段；不是 `varchar` 超长字段，更不能是 `text` 字段。
14. 【推荐】单表行数超过 500 万行或单表容量超过 2GB，才推荐分库分表（如果预计三年后的数据量根本达不到这个级别，不要在创建表时就分库分表）。
15. 【参考】合适的字符存储长度，不但节约数据库表空间、节约索引存储，更重要的是提升检索速度。

### （二）索引规约

1. 【强制】业务上具有唯一特性的字段，即使是组合字段，也必须建成唯一索引（不要以为唯一索引影响 insert 速度，这个速度损耗可以忽略，但提高查找速度是明显的；即使在应用层做了校验，没有唯一索引，根据墨菲定律，必然有脏数据产生）。
2. 【强制】超过三个表禁止 `join`。需要 `join` 的字段数据类型必须绝对一致；多表关联查询时，保证被关联的字段有索引。
3. 【强制】在 `varchar` 字段上建立索引时，必须指定索引长度，没必要对全字段建索引，根据实际文本区分度决定索引长度（一般对字符串类型数据，长度为 20 的索引，区分度会高达 90% 以上，可用 `count(distinct left(列名, 索引长度)) / count(*)` 确定）。
4. 【强制】页面搜索严禁左模糊或全模糊，需要的话走搜索引擎解决（索引文件具有 B-Tree 的最左前缀匹配特性，左边的值未确定无法使用此索引）。
5. 【推荐】有 `order by` 的场景，利用索引的有序性：`order by` 最后的字段是组合索引的一部分，并且放在索引组合顺序的最后，避免出现 `file_sort`。
6. 【推荐】利用覆盖索引进行查询，避免回表。
7. 【推荐】利用延迟关联或子查询优化超多分页场景（MySQL 不是跳过 offset 行，而是取 offset+N 行再丢弃前 offset 行）。
8. 【推荐】SQL 性能优化的目标：至少达到 `range` 级别，要求是 `ref` 级别，最好是 `consts`；`index`（全索引扫描）和 `ALL`（全表扫描）要避免。
9. 【推荐】建组合索引时区分度最高的放在最左边；如果 `where a=? and b=?`，a 列几乎接近唯一值，只需单建 `idx_a` 即可；存在非等号和等号混合时，把等号条件的列放在最前面。
10. 【推荐】防止因字段类型不同造成的隐式转换导致索引失效。
11. 【参考】创建索引时避免极端误解：索引宁滥勿缺（索引会降低写入速度、占空间）；抵制唯一索引（业务唯一的必须建）；过早优化，在不了解业务场景的情况下优化索引（先观察真实慢查询再建）。

### （三）SQL 语句

1. 【强制】不要用 `count(列名)` 或 `count(常量)` 替代 `count(*)`；`count(*)` 是 SQL92 定义的标准统计行数语法，并且会统计值为 NULL 的行，而 `count(列名)` 不统计 NULL。
2. 【强制】`count(distinct col)` 计算该列除 NULL 之外的不重复行数；`count(distinct col1, col2)` 如果其中一列全为 NULL，即使另一列有不同的值也返回 0。
3. 【强制】当某一列的值全是 NULL 时，`count(col)` 返回 0，但 `sum(col)` 返回 NULL，用 `sum()` 时注意 NPE，可以用 `IFNULL(SUM(column), 0)` 规避。
4. 【强制】用 `ISNULL()` 判断是否为 NULL 值；NULL 与任何值的直接比较结果都是 NULL（`NULL<>NULL` 返回 NULL，不是 true）。
5. 【强制】代码里写分页查询逻辑时，若 `count` 为 0 应直接返回，避免执行后面的分页语句。
6. 【强制】不得使用外键与级联，一切外键概念必须在应用层解决（外键与级联更新适用于单机低并发，不适合分布式、高并发集群；级联更新是强阻塞，存在数据库更新风暴的风险；外键影响数据库的插入速度）。
7. 【强制】禁止使用存储过程（难以调试、扩展，没有移植性）。
8. 【强制】数据订正（特别是删除、修改记录）时要先 `select`，避免误删，确认无误才执行更新语句。
9. 【推荐】`in` 操作能避免则避免；确实避免不了时，评估 `in` 后面集合元素的数量，控制在 1000 个之内。
10. 【参考】如有全球化需要，所有字符存储与表示均以 `utf8` 编码，注意字符统计函数的区别；需要存储表情时选 `utf8mb4`。
11. 【参考】`TRUNCATE TABLE` 比 `DELETE` 快、用的系统和事务日志资源少，但无事务、不触发 trigger，有可能造成事故，不建议在开发代码里使用。

### （四）ORM 映射

1. 【强制】查询时一律不要使用 `*` 作为字段列表，需要哪些字段必须明确写明（增加查询分析器解析成本；增减字段容易与 `resultMap` 配置不一致；无用字段增加网络消耗，尤其是 `text` 类型字段）。
2. 【强制】POJO 的布尔属性不加 `is`，而数据库字段必须加 `is_`，要求在 `resultMap` 里进行字段与属性之间的映射。
3. 【强制】不要用 `resultClass` 当返回参数，即使所有类属性名与数据库字段一一对应，也需要定义 `resultMap`；反过来，每一个表也必然有一个与之对应的 `resultMap`。
4. 【强制】`sql.xml` 配置参数使用 `#{}`（`#param#`），不要使用 `${}`，此种方式容易出现 SQL 注入。
5. 【强制】iBATIS 自带的 `queryForList(String statementName, int start, int size)` 不推荐使用（其实现方式是在数据库取到 `statementName` 对应的 SQL 语句的所有记录，再通过 `subList` 取 `start, size` 的子集合，容易内存溢出）；应在 SQL 里自行分页（`#start#, #size#`）。
6. 【强制】不允许直接拿 `HashMap` 与 `Hashtable` 作为查询结果集的输出。
7. 【强制】更新数据表记录时，必须同时更新记录对应的 `update_time` 字段值为当前时间。
8. 【推荐】不要写一个大而全的数据更新接口：传入 POJO，不管是不是自己的目标更新字段，都 `update table set c1=value1, c2=value2, c3=value3` 是不对的（易出错、效率低、增加 binlog 存储）。
9. 【参考】`@Transactional` 事务不要滥用：事务会影响数据库的 QPS；使用事务的地方需要考虑各方面的回滚方案，包括缓存回滚、搜索引擎回滚、消息补偿、统计修正等。
10. 【参考】`<isEqual>` 中的 `compareValue` 是与属性值对比的常量，一般是数字，表示相等时带上此条件；`<isNotEmpty>` 表示不为空且不为 null 时执行；`<isNotNull>` 表示不为 null 值时执行。

## 六、工程结构

### （一）应用分层

1. 【推荐】分层（上层依赖下层）：开放 API 层（可直接封装 Service 接口暴露成 RPC 接口，或通过 Web 封装成 HTTP 接口，网关控制层等）→ 终端显示层（模板渲染、JS 渲染等）→ Web 层（访问控制转发、基本参数校验、不复用的业务简单处理）→ Service 层（具体的业务逻辑）→ Manager 层（通用业务处理层：对第三方平台封装、对 Service 通用能力下沉如缓存方案和中间件通用处理、与 DAO 层交互对多个 DAO 的组合复用）→ DAO 层（数据访问层，与底层 MySQL、Oracle、HBase 等交互）；另有第三方服务与外部数据接口。**不跨层调用，不出现循环依赖。**
2. 【参考】分层异常处理：DAO 层异常类型多，用 `catch (Exception e)` 并 `throw new DAOException(e)`，不需要打印日志（日志由 Manager / Service 层捕获并打印）；Service 层出现异常必须记录出错日志到磁盘，尽可能带上参数信息，相当于保护案发现场；Manager 层与 Service 同机部署时与 DAO 层处理一致，单独部署则与 Service 一致；Web 层绝不应继续往上抛异常，如异常将导致页面无法正常渲染，直接跳转到友好错误页面并加上用户容易理解的提示；开放接口层要将异常处理成错误码和错误信息返回。
3. 【参考】分层领域模型：`DO`（与数据库表结构一一对应，通过 DAO 层向上传输数据源对象）、`DTO`（数据传输对象，Service 或 Manager 向外传输的对象）、`BO`（业务对象，由 Service 层输出的封装业务逻辑的对象）、`AO`（应用对象，在 Web 层与 Service 层之间抽象的复用对象模型）、`VO`（显示层对象，通常是 Web 向模板渲染引擎层传输的对象）、`Query`（数据查询对象，各层接收上层的查询请求；超过 2 个参数的查询封装，禁止使用 `Map` 类来传输）。

### （二）二方库依赖

1. 【强制】GAV 规则：`GroupID` 格式 `com.{公司/BU}.业务线.[子业务线]`，最多 4 级；`ArtifactID` 格式 `产品线名-模块名`；`Version` 遵循「主版本号.次版本号.修订号」（主版本号：不兼容的 API 修改；次版本号：向下兼容的功能性新增；修订号：向下兼容的问题修正）。
2. 【强制】线上应用不要依赖 `SNAPSHOT` 版本（安全包除外），保证发布的幂等性。
3. 【强制】二方库的新增或升级，保持除功能点之外的其他 jar 包仲裁结果不变；如果有改变，必须明确评估和验证（用 `mvn dependency:resolve` 前后对比）。
4. 【强制】二方库里可以定义枚举类型，参数可以使用枚举类型，但接口返回值不允许使用枚举类型或包含枚举类型的 POJO 对象。
5. 【强制】依赖一个二方库群时，必须定义一个统一版本变量，避免版本号不一致。
6. 【强制】禁止在子项目的 pom 依赖里出现相同 `GroupId`、相同 `ArtifactId`、不同 `Version`。
7. 【推荐】所有 pom 文件里的依赖声明放在 `<dependencies>` 语句块，所有版本仲裁放在 `<dependencyManagement>` 语句块。
8. 【推荐】二方库不要有配置项，最低限度不要再增加配置项。
9. 【参考】为避免应用二方库的依赖冲突，二方库发布者应简化二方库依赖导入、精简可传递的依赖、避免循环依赖。

### （三）服务器

1. 【推荐】高并发服务器建议调小 TCP 协议的 `time_wait` 超时时间。
2. 【推荐】调大服务器所支持的最大文件句柄数（fd）。
3. 【推荐】给 JVM 设置 `-XX:+HeapDumpOnOutOfMemoryError`，让 JVM 碰到 OOM 时输出 dump 信息。
4. 【推荐】线上生产环境 JVM 的 `Xms` 和 `Xmx` 设置为一样大小，避免 GC 后调整堆大小带来的压力。
5. 【参考】服务器内部重定向使用 `forward`；外部重定向地址使用 URL 拼装工具类生成。

## 七、设计规约

1. 【强制】存储方案和底层数据结构的设计获得评审一致通过，并沉淀成文档。
2. 【强制】需求分析阶段，如果与系统交互的 User 超过一类且相关的 UseCase 超过 5 个，使用用例图表达。
3. 【强制】某个业务对象的状态超过 3 个，使用状态图表达，并明确状态变化的各个触发条件。
4. 【强制】某个功能的调用链路上涉及对象超过 3 个，使用时序图表达，并明确各调用环节的输入与输出。
5. 【强制】系统中模型类超过 5 个且存在复杂依赖关系，使用类图表达，并明确类之间的关系。
6. 【强制】系统中超过 2 个对象之间存在协作关系且需要表示复杂处理流程，使用活动图表示。
7. 【推荐】需求分析与系统设计在考虑主干功能的同时，要充分评估异常流程与业务边界。
8. 【推荐】类在设计与实现时要符合单一职责原则。
9. 【推荐】谨慎使用继承扩展，优先使用聚合 / 组合；继承必须符合里氏代换原则（父类能出现的地方子类都能出现）。
10. 【推荐】系统设计阶段注意对扩展开放、对修改闭合。
11. 【推荐】共性业务或公共行为抽取成公共服务、公共类、工具类等，提高复用性和可维护性（和共享规范第 10 条「复用优先」一致：先查有没有，再新增）。
12. 【参考】避免误解：敏捷开发不等于讲故事 + 编程 + 发布，也不等于无文档。
13. 【参考】系统设计的主要目的是明确需求、理顺逻辑、后期维护，次要目的是指导编码。
14. 【参考】设计的本质是识别和表达系统难点，将难点逐一击破，最后形成文档。

## 八、团队补充规范（在手册之上，一并遵守）

1. **`Map` 必须写注释**：用到 `Map` 时写清 key 和 value 分别是什么（变量声明处或紧邻的行内注释）。
2. **方法必须有注释**：每个方法（含私有方法）都要有说明用途的注释；新增的类写创建者和日期。
3. **不写冗余的 `if / else`**：能提前返回、能合并条件、能用表达式的就不要写多余分支，避免增加后续维护成本。
4. **链接域名补全（一律按严重问题）**：图片地址、跳转链接等 URL 字段，必须通过项目里统一的方法补全域名（先搜有没有现成的拼接 / 补域名工具），不能把相对路径或写死的域名直接返回给前端。漏了会导致多环境、多机房资源访问失败，影响线上功能正确性和稳定性。
5. **个人信息不入日志**：日志里不打印手机号、邮箱、身份证号、token、密码等个人 / 敏感信息；必须打印时脱敏。
6. **代码复用**：同一段逻辑出现第 2 次就抽成公共方法或模块；新增前先查已有（见共享规范第 10 条）。
