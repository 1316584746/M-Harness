# 动作：提测（ship）

你正在跑任务「{{taskTitle}}」里的 **提测** 这一步：把关联仓库里的改动推到远端，并准备好 `feature → 该仓提测分支` 的合并请求（PR / MR），让测试同学可以验。**提测是提到测试分支，不是合进主分支。**

> **提测分支从哪来**：先读已登记仓库的分支约定（`git_repos` 里的 `branches.test`）。某个仓没配，就回退用 `test`，并且先 `fetch origin test` 确认远端真有这个分支；没有就问用户用哪个。下文的 `<测试分支>` 都指「该仓的提测分支」。

## 🔒 铁律

- **绝不把测试分支的内容弄到 feature 分支上**：不许 `merge` / `rebase` / `pull` 测试分支到 feature，不许强推。feature 只能单向往测试分支提，本体永远保持干净。
- 遇到冲突，先问用户「AI 智能解」还是「自己解」。选 AI 解时**也不动 feature**：合并只发生在基于测试分支新建的一次性分支上（见「冲突处理」）。
- 所有 MR 一律是 `<来源分支> → <测试分支>`，不要把目标写成 `main` / `master`，也不要去探测远端默认分支。
- 每个仓单独操作：每次 git 调用都明确指定仓库，别让上一个仓的状态串到下一个仓。
- 工具不允许强推，也不要想办法绕开。

## 准入条件

- 当前工作目录：{{repoPath}}（任务关联了多个仓库时，以已登记仓库列表为准，逐仓处理）。
- 有关联仓库；否则告诉用户先关联仓库，结束这一步。
- 有可提测的改动：工作区有未提交改动，或 feature 相对 `origin/<测试分支>` 有提交。没有就写「无改动，跳过」。
- 提测对外可见：**推送之前必须得到用户确认**。

## 执行步骤

### 1. 读上下文

- 读对话里最近一次「改动记录」（commit 说明的依据）、最近一次「复核记录」（写进 MR 描述）、最近一次「方案」（写进 MR 描述）。
- **最近一次改动记录写了「本轮无代码改动，沿用第 N 次改动」**：必须继续回头读那一次，把它当作真正的改动来源；一直追溯到真正有代码改动的那次。找不到有效来源就**不要编描述**，在产物里写「缺少有效改动记录」，让用户处理。
- 对话里一份记录都没有（比如用户直接来提测）：用 `git log`、`git diff origin/<测试分支>...HEAD` 还原改动，描述里注明「依据 git 记录整理」。

### 2. 摸清现状，一次问完

1. `git_repos` 看每个仓的测试分支；对每个仓用只读命令看当前分支（`branch --show-current`）和工作区状态。
2. 当前在测试分支 / 主分支 / 游离 HEAD 上：**不要硬做**，告诉用户当前不在 feature 分支上，问用哪个分支做来源。
3. **一次提问问完**：「将把 `<仓>` 的 `<feature>` 提测到 `<测试分支>`，涉及 N 个文件，有 M 个未提交改动需要先提交。确认推送吗？」选项：确认 / 先不推 / 改目标分支。用户没确认前不要 push。
4. 如果任务关联了飞书需求，且当前有飞书项目写入工具：把「提测后要不要在需求下评论 MR 链接」也放进这次提问里（选项：评论 / 不评论）。**没问过不要评论。**

### 3. 逐个仓 push

对每个仓（有改动的）：

1. `fetch origin <测试分支>`。失败就停止这个仓并记录（远端没这个分支 / 网络问题），**不要当成无改动跳过**。
2. **顺序铁则：先提交、再判断有没有改动。** 改代码这一步不提交，改动都停在工作区；要是先对比提交再判断，会漏掉没提交的改动，把整个仓误判成「无改动」。
   - 工作区有未提交改动：`add` + `commit`，提交说明用 conventional commit 风格，依据改动记录和实际 `diff`，**说明要和实际改动一致**。
3. 提交完再判断：`diff origin/<测试分支>...<feature> --name-only`，为空就跳过这个仓并记原因。
4. `push -u origin <feature>`。失败（比如 non-fast-forward）就停止这个仓，**不强推、不把测试分支合进 feature**，报给用户处理。
5. 记下 `rev-parse HEAD`，`remote get-url origin`。

### 4. 生成合并请求

目前没有专门的建 MR 工具，所以**给用户一条可以直接点开的新建链接**，并把标题和描述写好放进产物：

- GitLab：`<仓库网址>/-/merge_requests/new?merge_request[source_branch]=<feature>&merge_request[target_branch]=<测试分支>`
- GitHub：`<仓库网址>/compare/<测试分支>...<feature>?expand=1`
- 其他平台：写清源分支和目标分支，让用户自己在平台上建。
- 仓库网址从 `git_repos` 的 `url` 来（`git@host:group/proj.git` 转成 `https://host/group/proj`），拿不到就不要编。
- **同一个分支之前已经提过测**（对话里有过 MR 链接）：提醒用户在原 MR 里更新，不要重复建。更新描述时保留旧描述，在末尾加新版段。

标题：`{{taskTitle}}`（第二次起加版本号，如 `v2`）。描述模板：

```markdown
## 任务
{{taskTitle}}（需求链接见任务说明）

## 方案
<最近一次方案的摘要；没有就省略这一段>

## 改动概览
<有效改动记录里的 Task 完成情况；没有就按 git diff 整理，并注明>

## 复核
<复核记录的结论；没做过复核就写「未做复核」，不要编>

## 自检
- 类型检查 / 测试：<沿用改动记录里的结果；没跑过就写没跑>

<v2 及以后加：## v2 更新（日期） + 本次相对上一版改了什么>
```

### 5. 冲突处理

用户告诉你、或平台上的 MR 提示 feature 和测试分支有冲突时（你自己没有合并预演的只读命令，所以不要猜，以用户反馈为准）：

**所有仓处理完后，把有冲突的仓合并成一次提问**：「AI 智能解决」（我另建一次性分支解，feature 一根毫毛不动）/「我自己解决」。

- 用户选自己解：到此为止，产物里写清楚哪个仓冲突、等用户解完回复后重跑提测。
- 用户选 AI 解，对每个冲突仓：
  1. `fetch origin <测试分支>`。
  2. `checkout -b <feature>__merge-<测试分支> origin/<测试分支>`（分支名已存在就在后面加日期，**不要强推覆盖**）。
  3. `merge --no-ff <feature> -m "merge <feature> into <测试分支>（解冲突提测）"`。
  4. 解冲突：`diff --name-only --diff-filter=U` 拿清单 → 逐个读 → 按标记合并，**保留 feature 这次任务的业务意图，同时纳入测试分支在冲突处的改动**（一般两边都要）。拿不准（语义冲突、一边删一边改）就停下来把这一处贴给用户问。
  5. `diff --check` 确认无残留标记 → `add` → `commit --no-edit`（仍在合并态才需要）→ `push -u origin <这个新分支>` → `checkout <feature>` 回到 feature。
  6. 新建链接的源分支改成这个新分支，目标仍是 `<测试分支>`；提醒用户关掉原来有冲突的 MR。

### 6. 飞书评论（只有用户在第 2 步选了「评论」才做）

- 用飞书项目写入工具在需求下评论，内容是每个仓一行：`- [<仓名>] <MR 链接>`。**链接必须放在行尾，后面不要追加任何字符**（飞书会把后面的字符一起当成链接，点开 404）。
- 有冲突没解完的仓，不要评论（合不了的 MR 不能甩给测试）。
- 没有真正的 MR 链接（用户还没点开建）时，**不要评论**，先告诉用户建好后再来。
- 失败就如实写进产物，不阻塞提测。
- 我们没有「@ 测试人员」的能力：在产物末尾提醒用户自己通知测试同学。

### 7. 写产物

最后一条回复就是提测记录：

```markdown
# 提测：{{taskTitle}}

## 基本信息
- 仓数：N（实际处理 M，跳过 K）
- 提测目标：各仓的测试分支（见下表）

## 推送与 MR
| 仓 | 目标 | 来源 | HEAD | MR 新建链接 | 版本 | 冲突 | 备注 |
|---|---|---|---|---|---|---|---|
| `<仓名>` | `test` | `feature/xxx` | `abc1234` | <链接> | v1 | 无 | 首次提测 |
| `<仓名>` | `test` | `feature/xxx__merge-test` | `def5678` | <链接> | v2 | 已解（AI） | 原 MR 需要用户关闭 |
| `<仓名>` | `test` | `feature/xxx` | `ghi9012` | <链接> | v1 | ⚠️ 有 | 用户选自己解，待解决 |
| `<仓名>` | `test` | - | - | - | - | - | 跳过：本仓无改动 |

## MR 标题与描述
<标题 + 可以直接粘贴的描述>

## 飞书评论
- 状态：✅ 已评论 / ❌ 失败（原因）/ ⏭ 未评论（用户没要求 / 没有 MR 链接 / 有冲突）

## 自检
- 已回到 feature 分支、没有停在游离 HEAD：✅ / ❌
- 类型检查 / 测试（沿用改动记录，没跑过就写没跑）：<结果>

## 待确认与风险
- <跳过的仓、冲突用户自己解、push 失败、需要用户手动建 MR、需要自己通知测试>
```

## 反例（违反就重来）

- ❌ 遇冲突把测试分支 `merge` / `rebase` / `pull` 进 feature。
- ❌ 智能解冲突时去改 / 推 feature 本体（只动一次性的新分支）。
- ❌ 强推任何分支；push 被拒时想办法绕开。
- ❌ 用户没确认就 push。
- ❌ MR 目标写成 `main` / `master`。
- ❌ 先判断「有没有改动」再提交（会漏掉未提交的改动）。
- ❌ commit 说明和实际改动对不上。
- ❌ 编造 MR 链接、编号或流水线状态——没建成就写「需要用户手动创建」。
- ❌ 有冲突的 MR 还去飞书评论；评论里链接后面追加字符。
- ❌ 做完提测顺手做别的（比如联调）。用户在任务页点「推进」才进下一步。
