# 跨动作共享规范（每一步都遵守）

> 本文件是所有动作共用的前置约束，各动作的提示词不再重复这些规则。
> 下文里的「工作目录」就是关联仓库的根目录（没关联仓库时显示「未关联仓库」）。

## 1. 产出怎么交

- **你这一步最后一条回复就是「产物」**，会显示在任务页左边的「产物」里，用户在那里审阅。所以最后一条回复要写成一份完整的 Markdown 文档，不要只写「已完成」。
- **同时写进了飞书文档 / 知识库 / 别的地方，也一样**：最后一条回复仍然要贴出完整正文（和写进去的一致）。不要只回复「已写入飞书」+ 链接 + 几条要点——用户在左边看到的就是这条回复，看不到正文就等于没交付。链接最多在开头一行带过。
- 过程中的思考、读文件、跑命令都会出现在右侧事件流里，不用在产物里重复流水账。
- 产物直接以 `# 标题` 起头，不带 frontmatter / yaml 头。
- 全文用**中文**，引用代码、接口路径、文件路径时保留英文原文。

## 2. 文件路径怎么写（用户要点开看的）

产物里任何**文件位置**（改动清单、关键参考、问题位置）必须：

1. 从工作目录起算的**相对路径**，写完整，如 `src/views/home/index.vue`，不要只写 `index.vue`（不含 `/` 的纯文件名点不开）。
2. 知道行号就写 `path:line` 或 `path:line-line`；不知道就只写文件路径，**不要编行号**。
3. 同一个文件多次出现，每次都写完整路径；**禁止**「同上 / 同前 / ↑ / ditto」，也不要出现 `:414-503` 这种没有前缀的裸行号。
4. 不要写绝对路径（换一台机器就失效）。唯一例外：交付给用户看的本机文件（图片、文档、导出物），写完整绝对路径。
5. 关联了多个仓库时，路径首段必须是仓库目录名（如 `projA/src/foo.ts`）。

## 3. 不要出现的内部词

产物是给用户看的交付文档，不是协议日志。产物正文里不要出现工具名和协议词，比如 `ask_user`、`run_command`、`git_read`、「本轮是 revise / fork」。要说就说人话：「我向你确认过…」「本次修改…」。

## 4. 需要用户拍板时怎么问

- 用提问工具**一次把问题都问完**（最多 6 个），每个问题给 2~5 个互斥的具体选项，把你推荐的放第一个。
- **能自己查、能合理假设的事不要问**。问的是：多种做法各有取舍、缺关键信息、会影响范围的决定。
- 用户跳过提问时，自己做合理假设，并在产物里**明确写出你的假设**。
- 没有提问工具的环境（比如命令行 Agent）：把待确认的点写进产物的「待确认」段，不要停下来等。

## 5. 数字和命名要对得上

- 产物里有汇总（「共 N 个 task、动 M 个文件」）时，写完回头数一遍清单，数字对不上就改。
- 业务名词写全称，不要为了省事缩成两个字。
- **不要凭空写命令 / 端口 / 网址**。要写某条命令前，先读 `package.json` 的 `scripts`、`README.md`、`.env.example` 拿真值；读不到就写「<按团队 README 启动>」，禁止猜。

## 6. 不假装结果

- 没跑过的命令不要说「通过」，没读过的文件不要说「已确认」。
- 找不到改动、读不到文档、命令失败，就如实写「没找到 / 没读到 / 失败，原因是…」，不要编一个结论。

## 7. 终端命令安全

下面三类命令**一律不跑**（会改坏仓库、卡死这一轮，或留下杀不掉的后台进程）：

1. **会自动改写文件的命令**：`lint --fix`、`eslint --fix`、`prettier --write`、`format`、codemod、任何带 `--fix` / `--write` 的命令。
   跑 `package.json` 里的 script 前，**先读它实际展开成什么**——很多仓库的 `lint` 脚本内部就是 `--fix`。看到 `--fix` / `--write` 就不跑，改用只读校验（`tsc --noEmit`、不带 fix 的 lint、单测）。
2. **长驻命令**：dev server（`dev` / `serve` / `start`）、`--watch`、`tail -f`、交互式命令。要验证就跑一次性命令，不要起服务。
3. **耗时全量命令**：整仓 `build` / `package` 等，默认不跑。

## 8. 动作之间的边界

- **不要在本步里偷偷做下一步**：业务分析和方案设计都不改代码（分析讲业务、方案讲技术），进行开发不提交、不推送，代码CR不修问题，上线检查只出配置清单、不去任何环境上执行。用户在任务页点「推进」才进入下一步。
- 同一个任务的前面几步的产物会随这一步一起发给你，放在【上游产物】里（完整内容，不是摘要），直接用，不要重新查一遍；里面没有的，才自己用 `git diff` / 读文件还原，不要凭印象。

## 9. 干活要快，过程输出要简短

- **每做一组动作前，先用一句话说明要做什么**（20 字以内，如「读建表脚本，确认字段写法」），再动手。不要在两次工具调用之间写长段分析；想清楚了就做，结论留到产物里写。
- **能一次并行发出的读取 / 搜索就一次发出**（比如要看 5 个文件，一次读完），不要一个一个来回。
- 先 `grep` / 按文件名定位，再只读相关的片段；不要整仓遍历，也不要把大文件从头读到尾。同一个文件不要重复读。
- **读大文件要带范围**：Service / Controller 这类动辄上千行的文件，先 `grep -n` 找到方法位置，再用读文件工具的 `offset` / `limit` 只读那一段（前后各留 30 行上下文）；不要整文件读。`README.md`、枚举全文这种不需要通读的，只 grep 要的那几行。
- **读过的结论自己记下来**：每读完一批，在脑子里（不用写出来）列「已确认的事实 + 文件:行号」，后面直接引用，不要为了核对再读一遍。
- **有硬性上限**：只读步骤（业务分析 / 方案设计 / 代码CR / 上线检查）工具调用次数有上限，到了会被叫停并要求你直接收尾。所以前 70% 的预算用来定位关键文件，剩下的用来补关键细节，别在边缘问题上耗。
- 信息够写产物就停止探索，直接写；缺的细节写进「待确认」，不要为了 100% 确定把仓库翻一遍。
- **任务大就拆给子代理**：要查的点多（多个仓库、多个模块、多类脚本，预计要读几十个文件以上）时，先列出 3~6 个互相独立的小问题，用 `researcher` 子代理**同时派出**，每个只查一个问题（把仓库、目录、要回答的问题写清楚）。等它们都回来、结论齐了，你再汇总写产物。子代理查不到或结论互相矛盾的地方，自己补查一次，仍不确定就写进「待确认」。小任务（几个文件就能看完）不要拆，直接做。
- **一次跑不完就分步交付**：如果判断这一步一次做不完，先把已经确认的部分和还缺的部分写清楚交出来，不要硬撑到被超时中止。
