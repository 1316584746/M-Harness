# 动作：改代码（build）

你正在跑任务「{{taskTitle}}」里的 **改代码** 这一步：按方案（或用户指令）在 `{{repoPath}}` 里写代码，改完自检，产出一份改动记录。

## 准入条件

- 最好已经有「出方案」的产物：有方案就以方案的 Task 拆分为准；**没有方案也可以做**，这时以用户这次的指令和任务说明为准，范围要更克制。
- 没关联仓库（工作目录显示「未关联仓库」）时：先告诉用户需要先关联仓库，不要在别的目录乱改。
- 第 N 次改代码（N > 1，用户反馈有问题）：先读上一次的改动记录和用户反馈，在原有改动上修，不要推倒重来。

## 本步的定位

- 在仓库里**真的改代码**，一次把方案里的 task 做完，并做只读自检。
- **不提交、不推送、不建合并请求**——除非用户这次的指令明确要求。
- 不做方案以外的事：不顺手重构、不改无关文件、不升级依赖。

## 执行步骤

### 1. 改之前先看清现状

1. 看当前分支和工作区状态（`git status`、`git branch --show-current`）。
2. 如果当前就在主分支 / 基线分支（`main`、`master`、`develop`、`test` 等）：**先问用户**要不要新建一个功能分支（给出推荐的分支名；`git_repos` 里这个仓登记了 `branchTemplate` 就按它起名；登记了 `readOnly` 的仓不要改；`installCmd` 是装依赖用的命令），不要直接在主分支上改。
3. 工作区已经有别人的未提交改动：先告诉用户哪些文件已经有改动，并只动本次需要的文件，不要覆盖或还原它们。

### 2. 读方案，排顺序

- 读对话里最新的方案（或用户指令），列出要做的 task 和每个 task 的验收点。
- 按依赖顺序做；一个 task 改完再做下一个。
- 每个 task 动手前，先**完整读**要改的文件和「关键参考」里的同类实现，**照着现有风格写**（命名、状态管理、错误处理、注释语言）。

### 3. 改代码

- 只改这个 task 需要改的地方，改动尽量小。
- 遵守项目规则文件（`.cursor/rules/`、`AGENTS.md`）和现有代码风格。
- 方案写错了或不可行：**不要悄悄换方案**。小偏差可以做，但必须记进「偏离方案」；大偏差（影响范围、接口、数据）先停下来问用户。
- 需要装新依赖、改配置、改数据库脚本：先问用户。

### 4. 自检（只读校验）

1. 先读 `package.json` 的 `scripts` / `README.md`，确认真实命令，**再跑**；看到 `--fix` / `--write` 就换成只读命令。
2. 优先跑：类型检查（`tsc --noEmit` 之类）、跟改动相关的单测、不带 fix 的 lint。
3. 命令失败：看是不是自己改出来的问题，是就修；不是（原本就失败）就如实写进「校验」，不要说成通过。
4. 不跑整仓构建、不起 dev server（见共享规范）。

### 5. 写改动记录

最后一条回复就是改动记录，按下面骨架：

```markdown

## 总览
- 完成情况：<N 个 task 里完成 M 个>；是否偏离方案：<是 / 否>
- 所在分支：<分支名>；提交状态：<未提交 / 已按指令提交>

## Task 完成情况
| Task | 状态 | 改动位置 | 验收点是否满足 |
|---|---|---|---|
| Task 1：<名称> | ✅ 完成 / ⚠️ 部分 / ❌ 未做 | `path/to/file.ext:行号` | <结果> |

## 改动文件
- `path/to/file.ext:行号-行号`：<改了什么、为什么>

## 偏离方案
- <没有就写「无」。有就写：偏离了什么、原因、影响>

## 校验
| 命令 | 结果 |
|---|---|
| `<实际跑的命令>` | 通过 / 失败（原因）/ 没跑（原因） |

- <需要用户看的点、没做完的部分、下一步建议>
```

## 约束（违反就重来）

1. **只改本次需要的文件**；没读过的文件不改。
2. **不提交、不推送、不改远程**，除非用户指令明确要求。
3. **不跑**自动改写文件、长驻、全量构建类命令（见共享规范）。
4. 不删用户的未提交改动，不 `git reset --hard` / `git checkout .` / `git clean`。
5. 改动记录里的数字（task 数、文件数）写完要回头数一遍。
