# 动作：联调（dev）

你正在跑任务「{{taskTitle}}」里的 **联调** 这一步：把关联仓库里这次的改动送到该仓的**联调分支**，让联调环境的流水线跑起来。

两种送法，**由用户选，不要自己挑**：

- **直推**：基于最新的 `origin/<联调分支>` 切到游离 HEAD，把 feature 合进去，直接推到 `origin/<联调分支>`。最快，不留合并请求。
- **提 PR**：把 feature 推到远端，然后创建 `feature → <联调分支>` 的合并请求（PR / MR）。

> **联调分支从哪来**：先读已登记仓库的分支约定（`git_repos` 里的 `branches.integration`）。**没配联调分支的仓，这一步跳过**，在产物里写「跳过：未配联调分支」，不要猜一个。下文的 `<联调分支>` 都指「该仓配置的联调分支」。

## 🔒 铁律

- **绝不把联调分支的内容弄到 feature 分支上**：不许 `merge` / `rebase` / `pull` 联调分支到 feature，不许强推。feature 永远保持干净，只单向往联调分支送。
- 合并（feature → 联调分支）只发生在**别的位置**，不碰 feature 本体：
  - 直推：在 `origin/<联调分支>` 的游离 HEAD 上合并 feature。
  - 提 PR：无冲突时在平台上合；有冲突走下面「冲突处理」里的一次性分支。
- **不要在本地创建 / 重置 / 移动本地的联调分支**（不要 `checkout -B <联调分支>`、`checkout -b <联调分支>`、`branch -f`、`reset`）。要联调分支的内容一律用 `origin/<联调分支>` 或游离 HEAD，否则会把你本地同名分支改掉，弄丢还没推的东西。
- 只做用户选的那一种方式，不要两种都做；工具不允许强推，也不要想办法绕开。
- 每个仓单独操作：每次 git 调用都明确指定仓库，别让上一个仓的状态串到下一个仓。

## 准入条件

- 当前工作目录：{{repoPath}}（任务关联了多个仓库时，以已登记仓库列表为准，逐仓处理）。
- 有关联仓库，且至少有一个仓配了联调分支；否则直接如实告诉用户缺什么，结束这一步。
- 有改动可送：工作区有未提交改动，或 feature 相对 `origin/<联调分支>` 有提交。没有就写「无改动，跳过」。

## 执行步骤

### 1. 摸清现状，然后一次问完

1. 用 `git_repos` 看有哪些仓、各自的联调分支；对每个仓用只读命令看当前分支（`branch --show-current`）和工作区状态（`status`）。
2. 当前在联调分支 / 主分支 / 游离 HEAD 上：**不要硬做**，告诉用户「当前不在 feature 分支上」，问他要用哪个分支作为来源。
3. 把下面这些**一次提问问完**：
   - 送法：直推 / 提 PR（推荐：用户没说过倾向时，推荐「提 PR」，更稳）。
   - 确认清单：「将把 `<仓>` 的 `<feature 分支>` 送到 `<联调分支>`，涉及 N 个文件，需要先提交的未提交改动有 M 个」，让用户确认可以推。
4. 推送是对外可见的动作，**用户没确认之前不要 push**。

### 2. 逐个仓处理

对每个配了联调分支、且有改动的仓，依次：

1. `fetch origin <联调分支>`。失败就停止这个仓并如实记录（远端没这个分支 / 网络问题），**不要当成无改动跳过**。
2. 工作区有未提交改动：先 `add` + `commit`，提交说明用 conventional commit 风格，内容依据最近一次「改动记录」和实际 `diff`，不要写空话。
3. 用只读命令判断相对联调分支有没有改动（`diff origin/<联调分支>...<feature> --name-only`）。没有就跳过。

#### 方式 A：直推

1. 记下 feature 分支名（`branch --show-current`）。
2. `checkout --detach origin/<联调分支>`（只用游离 HEAD，不建任何本地联调分支）。
3. `merge --no-ff <feature> -m "merge <feature> into <联调分支>（联调）"`。
4. **没冲突**：`push origin HEAD:refs/heads/<联调分支>`（目标写全名，避免和同名标签歧义）。推完记下 `rev-parse HEAD`，再 `checkout <feature>` 回到 feature。
   - push 被拒（别人刚推过，non-fast-forward）：先 `checkout <feature>` 回来，告诉用户重跑联调，**绝不强推**。
5. **有冲突**：不要先 push，走「冲突处理」。

#### 方式 B：提 PR

1. `push -u origin <feature>`，失败就停止这个仓并记录，不强推、不把联调分支合进 feature。
2. 创建 `<feature> → <联调分支>` 的合并请求。目前没有专门的建 PR 工具，所以**给用户一条可以直接点开的新建链接**：
   - GitLab：`<仓库网址>/-/merge_requests/new?merge_request[source_branch]=<feature>&merge_request[target_branch]=<联调分支>`
   - GitHub：`<仓库网址>/compare/<联调分支>...<feature>?expand=1`
   - 其他平台：写清楚源分支、目标分支，让用户自己在平台上建。
   - 仓库网址从 `git_repos` 里的 `url` 来（`git@host:group/proj.git` 要转成 `https://host/group/proj`），拿不到就不要编。
3. 标题建议：`[联调] {{taskTitle}}`；描述要写：任务链接、方案摘要、改动概览、自检结果（从前面几步的产物里提炼，没有的段就不写）。把标题和描述一并放进产物，方便用户粘贴。
4. 用户之前已经建过同分支的 PR：提醒他在原 PR 里更新描述，不要重复建。

### 3. 冲突处理（两种方式共用）

所有仓跑完后，有冲突的仓**合并成一次提问**问用户：「AI 智能解决」还是「我自己解决」。

解冲突的原则：用只读命令拿冲突文件清单（`diff --name-only --diff-filter=U`）→ 逐个读文件 → 按 `<<<<<<<` / `=======` / `>>>>>>>` 合并，**保留 feature 这次任务的业务意图，同时纳入联调分支在冲突处的改动**（一般两边都要，不是二选一）→ 拿不准（语义冲突、两边逻辑互斥、一边删一边改）就停下来，把这一处贴给用户问怎么取舍。

- **直推 + AI 解**：此刻已经在 `origin/<联调分支>` 游离 HEAD 的合并冲突态，就地解：确认无残留标记（`diff --check`）→ `add` → `commit --no-edit` → `push origin HEAD:refs/heads/<联调分支>` → `checkout <feature>`。push 被拒同上，回 feature、让用户重跑。
- **提 PR + AI 解**：在一次性的新分支上解，feature 不动：
  1. `checkout -b <feature>__merge-<联调分支> origin/<联调分支>`（分支名已存在就在后面加日期，不要强推覆盖）。
  2. `merge --no-ff <feature>`，按上面的原则解冲突并提交。
  3. `push -u origin <这个新分支>`，`checkout <feature>` 回来。
  4. 新建链接的源分支改成这个新分支，目标仍是 `<联调分支>`，并提醒用户关掉原来冲突的 PR。
- **用户选自己解**：直推先 `merge --abort` 再 `checkout <feature>` 回到 feature（两步分开执行）；提 PR 保持现状，等用户解完回复后重跑联调。

### 4. 收尾自检并写产物

- 确认每个仓都已经回到 feature 分支（没停在游离 HEAD）、没有创建本地联调分支（`branch --show-current`、`status` 看一眼）。
- 最后一条回复就是联调记录：

## 反例（违反就重来）

- ❌ 把联调分支 `merge` / `rebase` / `pull` 进 feature。
- ❌ 强推任何分支，或者 push 被拒时想办法绕开。
- ❌ 用户还没确认就 push。
- ❌ 自己挑直推还是提 PR，或者两种都做。
- ❌ 对没配联调分支的仓硬推，或者猜一个分支名。
- ❌ 在本地创建 / 重置联调分支。
- ❌ 编造 PR 链接、合并请求编号或流水线状态——没建成就写「需要用户手动创建」。
- ❌ 做完联调顺手去「提测」。用户在任务页点「推进」才进下一步。
